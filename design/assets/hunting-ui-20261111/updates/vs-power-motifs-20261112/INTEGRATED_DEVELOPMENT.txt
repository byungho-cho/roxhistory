3. 준비 화면의 최신 전투력 헤더

선택본은 2442:1565이며 준비 화면 1920×1080 기준 (480,20), 960×198입니다. 숨김 보존된 60% 시안이나 이전 HP형 준비 헤더는 사용하지 않습니다.
- 통합 붓터치: 헤더 내부 (124,6), 712×178, 본체 불투명도 70%.
- 문양과 미세 섬유는 별도 레이어이며 붓터치 alpha 영역으로 마스킹합니다. 과거 구름 모양 장식은 숨김 유지.
- 돌도끼·토기·목판은 각각 독립 그룹으로 켜고 끌 수 있게 합니다. 문양 위치·크기·opacity는 layout.json을 사용합니다. 문양 자체 opacity 0.55가 SVG에 들어 있고 화면 인스턴스 opacity 0.75를 추가 적용합니다. 이미 들어간 opacity를 중복 곱하지 마세요.
- 사냥꾼 초상: (276.4,40.8),102.4×102.4. 사슴 머리: (586,15.75),96×126. 내보낸 PNG는 이전 큰 원본 해상도를 유지하며 현재 크기로 한 번 축소해 사용합니다.
- 새 VS 조합: (422.6,40.6),114.8×114.8. 164×164 공통 조합의70%이며 렌더 외곽은140×140입니다.
- 전투력 숫자는 별도 글리프를 조합합니다. 현재 코드에는 0·1·2·3·8·쉼표만 등록돼 있으므로 0–9 전체를 지원하도록 바꿉니다.
- 시안의 12,300 / 8,000은 예시입니다. 실제 출전 편성과 적 데이터에서 값을 가져오며 데이터 변경 시 갱신합니다. 확정되지 않은 전투력 산식이나 밸런스 수치를 이 이미지에서 추정해 고정하지 않습니다.
- 산식이 아직 없으면 표시용 계산을 별도 함수·설정으로 격리하고, 사용할 스탯/가중치/합산 규칙을 제안하여 확인받습니다. 전투력 숫자를 피해량·승률·HP로 곧바로 사용하지 않습니다.
- 숫자 길이가 바뀌면 아이콘+숫자 전체를 좌우 기준점에 다시 가운데 정렬합니다. 0, 999, 1,000, 12,300, 999,999와 최소 지원 화면 크기를 검증합니다. 긴 값 표기 규칙은 임의로 생략하지 말고 제안합니다.

기존 3인 편성, 적 자동배치, 바닥 축을 공유하는 3×3 배치 격자, 출전 초상과 하단 사냥 준비·가방, 빠른 출전·사냥 시작은 보존합니다. 위치를 이번 연출 때문에 임의로 다시 확정하지 않습니다. 준비 전투력과 전투 중 현재/최대 HP는 별개입니다.


3-1. 화면 가장자리20px 정렬

20px는 상단 한 곳만이 아니라1920×1080 화면의 각 가장자리를 기준으로 합니다. 그림자까지 포함한 실제 렌더 외곽을 사용하며,960×540 게임 디자인 좌표로는10px입니다. 화면 비율과 safe area 변환을 한 번만 적용하고, 노치/시스템 영역에서는 안전 영역 안쪽으로 보정합니다.
현재 Figma에서 확인한 위치:
- 좌상단 숲 가장자리 제목/뒤로가기 그룹: (20,20),440×112.
- 좌측 출전 편성 패널: (20,159),330×710. 우측 패널로 바꾸지 않습니다.
- 하단 사냥 준비 현판+가방 그룹: (20,936),330×124. 가장 아래1060이므로 하단20px.
- AUTO/X2 그룹: (1696,20),204×96. 가장 오른쪽1900이므로 우측20px.
- 빠른 출전 버튼 논리 영역: (1232,954),320×100. 그림자 포함 (1229,954),326×106.
- 사냥 시작 버튼 논리 영역: (1577,954),320×100. 그림자 포함 (1574,954),326×106. 오른쪽1900·아래1060이므로 우측/하단20px.
- 준비 전투력 헤더: (480,20),960×198, 화면 중앙 축에 정렬.
새 돌도끼 모양 숫자 배경은 검토 중인 미확정 시안입니다. 이번 인계·구현에는 넣지 않고 현재 확정된 붓터치/숫자 디자인을 유지합니다.

4. 새 VS 조합과 연출

옛 배경 아이콘과 V/S를 새 3조각으로 교체합니다. 준비/전투가 같은 원본을 사용하되 크기만 다르게 조합합니다.
- 공통 논리 조합 164×164.
- 좌우 창은 고해상도 단일 창 원본 PNG400×400을 각각 독립 TextureRect/노드로 재사용합니다. 공통164×164 조합 안에서 각 창의 표시 영역은 (-18,-18),200×200이며 오른쪽만 수평 반전합니다. 좌우 이동·회전·opacity·pivot은 각각 독립 제어합니다. 통짜 교차창 이미지로 애니메이션을 구현하지 않습니다. 원본72% 불투명도가 PNG에 이미 반영됐으므로 중복 적용하지 않습니다.
- V 논리 100×104를 0.82배로, 조합 내부 (5,32)에 배치합니다.
- S 논리 100×104를 0.82배로, 조합 내부 (73,56)에 배치합니다.
- SVG 내보내기 외곽은 그림자 포함 102×106입니다. 특히 S는 왼쪽 render offset -1.5px가 있으므로 manifest/layout 기준으로 맞춥니다.
- 현재 전투 HUD의 72×72 VS 슬롯에는 공통 조합을 72/164배로 적용합니다. 전체 HUD와 HP 바의 현행 위치를 불필요하게 바꾸지 않습니다.
- 애니메이션 pivot은 각 조각의 논리 중심으로 두고, 그림자 바운드 때문에 V/S 착지 위치가 흔들리지 않게 합니다.

4-1. 최신 확정 방향: 사냥 준비 진입 매칭 전환

이번 연출은 사냥 준비 화면에 진입하는 시점에 적용합니다. 이 경로에서만 기존 구름 페이드를 매칭 전환으로 교체합니다. 기존 게임 시작·인트로의 구름 연출과35초 인트로는 유지합니다. 전투 시작 후의 접근·카메라 흐름까지 같은 연출로 바꾸지 않습니다.

순서:
1) 준비 전장 배경과 필수 에셋을 미리 준비합니다. 화면에 올릴 준비가 끝나기 전에 중앙 연출을 시작하지 않습니다.
2) 화면 정중앙에 전투력 헤더의 붓터치 배경이 뒤에서 앞으로 확대되며 등장합니다. 전장 배경 자체를 확대하는 것이 아니라 헤더 배경/매칭 묶음의 등장입니다.
3) 양쪽 캐릭터 초상이 짧은 간격으로 순차 등장합니다. 사냥꾼과 사슴은 독립 레이어로 제어합니다.
4) 왼쪽 창과 오른쪽 창이 각각 날아와 교차하고, 그 교차 순간에 VS가 짧은 번개 효과와 함께 등장합니다. V/S도 독립 레이어를 유지하지만 이전의 길게 나뉜 V→S 소개를 여기에 중복해 넣지 않습니다.
5) 중앙의 매칭 묶음 전체가 축소되며 상단 확정 위치(헤더 원점480,20)로 이동합니다. 배경·문양·초상·숫자·창·V/S를 공통 부모 아래 두고 상대 좌표를 유지합니다.
6) 상단 정착에 맞춰 제목/뒤로가기, 좌측 편성 패널, 격자와 하단 현판·가방, 버튼·AUTO/X2 등 나머지 UI를 짧게 순차 표시합니다. 실제 선택·터치가 가능해지는 시점이 시각 완료와 일치해야 합니다.

연출 순서는 확정 방향이고 세부 시간·스케일·easing은 가안입니다. 초기 제안은 배경120–180ms, 초상 순차 각100–150ms, 창 교차와 VS120–180ms, 상단 축소 이동200–300ms, 나머지 UI150–250ms를 일부 겹쳐 전체 약0.9–1.3초로 구성합니다. 고정 대기 시간을 로딩처럼 추가하지 말고 실제 기기에서 더 짧게 조정할 수 있게 설정을 분리합니다.
번개는 새 확정 비트맵이 아닙니다. 기존 효과를 재사용하거나 짧은 벡터/셰이더 효과로 제안 구현하고, 전체 화면의 강한 반복 섬광 대신 교차 지점의 절제된 빛으로 제한합니다. 본 묶음에는 번개 원화/효과음이 포함되지 않습니다.

로딩·입력·중단:
- 가능하면 진입 전에 비동기 preload하고 첫 프레임 텍스처 업로드 지연을 확인합니다. 준비가 늦으면 현재 화면/안정적인 전장 배경과 명확한 준비 표시를 유지하며 빈 화면·부분 UI·멈춘 연출을 보여주지 않습니다. 임의의 가짜 다운로드 진행률을 만들지 않습니다.
- 연출 중 편성·시작·AUTO/X2 입력은 중복 실행되지 않도록 제한합니다. Android 뒤로가기/취소는 처리하며, 연출을 중단했다면 scene/tween/callback과 입력 잠금을 반드시 정리합니다.
- 앱 중단/복귀·해상도 변경·연타·재진입·리소스 실패에서 최종 위치와 입력 가능 상태를 복구합니다. 사용자 입력을 장시간 묶지 않습니다.
- 반복 진입 시 매번 재생/축약/스킵 정책은 아직 미정입니다. 제안 정책을 명시하고 확인하며 임의로 영구 설정하지 않습니다.
- 현재 전투 시작의 약2.4초 상호 접근·카메라 하강/줌은 보존합니다. 준비 진입 연출과 전투 진입을 연달아 중복 재생하지 않습니다. 기존 HP 바의 좌우 매칭 강조를 유지할 때도 짧게 하고 숫자·초상·VS를 가리지 않게 합니다.
- 저사양 실기기에서 첫 진입/재진입 frame time, shader compile/texture upload, 메모리, 파티클·overdraw, 배터리·발열을 확인합니다. 디자인만 보고 성능 향상을 보장하지 않습니다.

5. 기존 전투 기능 보존

현행 구현된 AUTO의 강타/협동 예약, X2, 3구슬, 강타1/협동2 비용, 약1초 잠금, 충전음·반짝임, 접근·카메라 하강/줌·강타/협동 강조, 종료 확인을 유지합니다. 이미 구현된 것을 옛 기획 수치로 되돌리지 마세요.
- 시작 후 격자 걷힘 → 아군과 적 상호 접근 → 사거리 안 자동 교전과 타격 동기화.

- 종료 확인은 현재 전투 장면 위에 뜹니다. 제목 “전투를 종료할까요?”, 본문 설명 없음, 메탈 “종료”와 금색 “계속”. 오래된 배경 캡처를 붙이지 않습니다.

- 실패·취소·재시도 시 타이틀 시작 입력과 팝업 중복 차단을 정상 해제하고, 기존 유효 패치와 세이브는 보존합니다.

7. APK와 PCK를 분리한 업데이트 구조

공통 화면은 재사용하되 artifact kind, 상태 머신과 완료 의미는 구분합니다.
PCK: 확인 → 다운로드 → 서명/크기/해시/호환 검증 → 패치 준비 완료 → 재실행 → 호환 패치 mount.
APK: 확인 → 다운로드 → APK 검증 → 설치 준비 완료 → Android 설치 허용/시스템 설치 확인 → 실제 앱 교체 → 다음 실행에서 설치 버전 검증.

APK 파일을 PCK로 mount하거나 APK 설치를 “재실행” 버튼만으로 처리하지 마세요. 네이티브 앱 버전과 실제 적용 콘텐츠(PCK) 버전을 각각 보관하고 표시합니다.
- 설치된 네이티브 versionCode/versionName/package/signing identity는 Android PackageManager에서 읽습니다.
- ProjectSettings의 application/config/version은 mounted PCK가 바꿀 수 있어 설치된 APK 버전 판정에 사용하지 않습니다.
- 기존 0.2.117 소스 versionCode는116입니다. 다음 APK는 실제 대상 기기의 설치 code보다 높아야 하며 단순히117로 가정하지 않습니다.
- 기존 패키지 com.roxhistory.demo와 서명 연속성을 유지합니다. 현재 개발 릴리스는 기존 MY-NUROX 개발 키로 서명된 상태이므로 실제 설치 기기와 새 APK 인증서 지문 일치를 확인합니다. 키·비밀번호를 지시문/로그/저장소에 기록하지 않습니다.
- 서명 불일치를 해결하려고 자동 삭제 후 재설치하지 않습니다. 삭제는 사용자 데이터를 잃을 수 있습니다.

현재 소스에는 APK 설치용 native bridge, REQUEST_INSTALL_PACKAGES, 설치 결과/설정 복귀 처리가 없습니다. PCK는 Android manifest 권한이나 Java/AAR 코드를 추가할 수 없으므로 이 기능을 포함한 새 APK를 최초 한 번 외부 경로로 설치해야 합니다. 그 이후부터 앱 내부 다운로드·시스템 설치 연결이 가능합니다. 설치 안내에서 이 초기 조건을 명확히 합니다.

8. 앱 내 APK 다운로드와 신뢰

기존 PCK 서명 검증을 약화시키지 않습니다. APK용 별도 서명된 catalog/schema/channel을 둡니다. 기존 PCK latest.json 형식을 APK 내용으로 덮어써 구버전 클라이언트를 깨뜨리지 마세요.

APK 카탈로그는 최소 artifact type, package ID, versionName/versionCode, 소스 commit, 정확한 release asset 경로, byte length, SHA-256, 지원 Android/ABI, 서명 identity 또는 검증 가능한 signer 조건을 묶어 검증합니다. HTTPS나 파일명만 믿지 않습니다. 기존 신뢰 루트/키 관리 방식을 검토하여 명시적으로 설계하고, 개인키를 앱에 넣지 않습니다.
- 최근 릴리스는 prerelease입니다. GitHub /releases/latest만 호출하면 원하는 빌드를 놓칠 수 있으므로 서명된 명시적 채널을 사용합니다.
- immutable 버전별 APK 업로드 → 업로드한 bytes/해시 검증 → 마지막에 서명된 채널 포인터 갱신. live catalog가 가리키는 파일을 보존합니다.
- 예상 저장소/호스트/자산만 허용하고 redirect 후 대상도 검증합니다. 인증 토큰이나 임의 다운로드 URL을 저장·노출하지 않습니다.
- 앱 전용 저장공간의 .part에 스트리밍하고 충분한 여유 공간을 먼저 확인합니다. 완료 후 길이/해시 및 APK package/versionCode/signer/플랫폼을 확인한 파일만 설치 가능한 상태로 전환합니다.
- 검증과 큰 파일 해시는 UI 스레드를 막지 않게 합니다. 취소·중단·프로세스 종료 후 부분 파일 정리와 재시도 정책을 명확히 합니다. 검증된 이전 앱/패치는 삭제하지 않습니다.
- 0.2.117 APK는 약474MB(473,794,869 bytes)입니다. 현행 PCK의 다운로드 30초 timeout을 그대로 적용하지 말고 연결/무응답/전체 전송 정책을 큰 APK와 느린 네트워크에 맞춰 검토합니다. 근거 없이 timeout을 무한대로 두지 않습니다.
- 현재 0.2.117 APK release metadata SHA-256: 4442a53666107032c835a27a48fbed25d927bd95ee9779a2557c538cbef6eef1. 이 값은 조사 기준이며 다음 APK에는 새 검증값을 사용합니다.

9. Android 설치 연결

Godot 업데이트 상태와 Android 네이티브 설치 처리를 분리한 bridge를 만드세요. 기존 VillageAlarm 알림/진단 bridge에 설치 기능이 있는 것으로 가정하지 않습니다. 기존 빌드 스크립트와 AAR 패키징에 새 bridge가 실제로 들어가도록 연결하고 merged manifest를 검증합니다.

필요 기능:
- 실제 설치 package/versionCode/versionName와 capability 조회.
- 설치 허용 여부 확인 및 앱 전용 설정 화면 열기.
- 검증된 APK만 시스템 설치로 넘기기.
- 설치 결과/보류 상태, 설정 복귀, Activity 재생성, 프로세스 종료 후 복구 처리.

Android 8+에서 REQUEST_INSTALL_PACKAGES 및 canRequestPackageInstalls()를 적절히 사용합니다. 허용되지 않았으면 이유를 게임 팝업으로 설명하고 RoxHistory 전용 ACTION_MANAGE_UNKNOWN_APP_SOURCES 설정을 엽니다. 복귀 시 상태를 다시 확인합니다. 최초 다운로드에 쓴 Chrome의 설치 허용은 RoxHistory의 허용과 별개입니다.
사용자가 설정을 거절하거나 뒤로 돌아오면 강제 반복하지 않고 나중에/다시 시도 선택을 제공합니다. 보안 설정을 자동 변경하거나 사용자 확인을 우회하지 않습니다.

명시적 결과 처리를 위해 PackageInstaller session 방식을 우선 검토합니다. 이 방식은 FileProvider가 필수는 아닙니다.
- API31+ USER_ACTION_REQUIRED 및 STATUS_PENDING_USER_ACTION을 처리하고 Android 시스템 설치 확인은 사용자가 수행합니다.
- API35+ commit callback의 PendingIntent 요구사항을 확인합니다. 기존 알림 bridge의 FLAG_IMMUTABLE을 그대로 복사하면 설치 callback이 거부될 수 있으므로 범위를 제한한 올바른 mutable callback을 사용합니다.
- Intent 방식으로 구현한다면 좁은 APK 디렉터리만 공유하는 non-exported FileProvider와 일시적 읽기 권한의 content:// URI를 사용합니다. file://나 전체 저장소 노출은 금지합니다.
- Android 시스템 승인/설치 화면은 게임 스킨으로 바꿀 수 없습니다. 앞뒤 안내만 공통 게임 팝업을 사용합니다.
- 설치 요청 성공은 설치 완료가 아닙니다. 취소/실패는 기존 앱·저장 데이터를 유지하고 명료하게 알립니다.
- 앱 교체 시 기존 프로세스가 종료될 수 있습니다. 자동 재실행을 보장하지 말고 “설치 후 게임을 다시 열어 주세요” 또는 시스템의 열기를 안내합니다.
- pending install metadata를 최소한으로 저장하고 다음 실행에서 실제 versionCode를 검증한 후에만 성공으로 처리합니다. 이후 검증된 임시 APK를 정리합니다.
- 새 APK가 구 PCK를 무조건 다시 mount하지 않도록 native capability/runtime/base 호환성을 명시합니다. 새 APK에서 이전보다 최신 콘텐츠를 잃거나 호환되지 않는 overlay를 덮어쓰는 경우를 테스트합니다.

이 흐름은 GitHub 직접 배포/사이드로드용입니다. Google Play 배포는 자체 업데이트·REQUEST_INSTALL_PACKAGES 정책이 다르므로 동일 플로를 그대로 포함하지 말고 배포 채널별로 분리 검토합니다.

10. 기존 PCK 보안과 부트스트랩을 유지

현행 bootstrap은 pinned public key로 signed JSON envelope를 확인하고, base0.2.91·기준commit9c97f052…·runtime godot-4.5.1-android-pck-2, PCK 파일명, 정수 크기 상한600MB, SHA-256과 더 최신 버전을 검증합니다. 구체 상수와 검증 순서는 실제 코드를 읽고 유지합니다.
- unsigned JSON 허용, 검증 실패 무시, 호환 조건 삭제는 하지 않습니다.
- 검사4초/다운로드30초 timeout, 취소 .part cleanup, generation guard, 임시 인덱스 rename, 검증된 cache의 main scene 이전 mount, 기존 재실행 흐름을 회귀 검사합니다.
- PCK UI는 PCK를 받기 전에 필요합니다. 새 UI/폰트/버튼 및 native bridge가 기본 설치 APK에 포함되게 하고, 아직 다운로드하지 않은 PCK 안 자산만 preload하는 순환 의존을 만들지 않습니다.
- 이미 실행 중인 bootstrap 스크립트를 그 bootstrap이 뒤늦게 mount한 PCK가 완전히 교체한다고 가정하지 않습니다.
- 구버전 클라이언트의 기존 서명 PCK 채널을 유지하면서 새 native APK/새 runtime 전환 정책을 문서화합니다.
- 조사에서 v0.2.117의 PCK asset metadata(51,312,180 bytes)는 확인했지만 latest.json payload/signature는 커넥터404로 독립 검증하지 못했습니다. 개발자는 실제 게시 manifest와 설치 기기의 mount 결과를 직접 검증하고 결과를 보고해야 합니다.

11. 상태별 문구와 버튼

구현 상태 enum과 문구를 한 곳에서 관리합니다. 아래는 기능 의미를 고정한 제안이며 실제 크기와 정확한 표기는 Figma와 대조합니다.
- 앱 업데이트 발견: “앱 업데이트”, 현재/새 버전, 실제 다운로드 크기, “나중에 / 다운로드”.
- 다운로드 중: 실제 %와 MB, “다운로드 취소”. 닫기/뒤로가기 역시 취소라는 현재 정책을 일관되게 표현.
- 검증 중: “파일 확인 중”. 다운로드 100%와 설치/패치 적용 완료를 혼동하지 않음.
- PCK 준비: “패치 준비 완료”, “재실행 후 적용됩니다”, “나중에 / 재실행”.
- APK 준비: “설치 준비 완료”, “Android 설치 화면에서 확인해 주세요”, “나중에 / 설치하기”.
- 설치 허용 필요: “이 앱의 설치 허용이 필요합니다”, “나중에 / 설정 열기”.
- 시스템 설치 요청 뒤: “설치 확인 대기”. 시스템 설치/취소 결과를 기다림.
- 설치 실패/취소: 결과에 맞는 간결한 사유, 기존 앱으로 돌아가거나 다시 시도.
- 다음 실행 후 native versionCode가 실제 갱신됐을 때만 완료 표시.

같은 popup shell을 쓰되 제목·설명·version source·진행·버튼 enabled·취소 가능 여부를 상태 모델에 연결합니다. UI를 닫았다고 다운로드·설치 콜백이 유실되어 다른 화면을 덮지 않도록 합니다.
