# RoxHistory 개발 설계 검토안 v0.1

상태: 구현 전 검토안. React·TypeScript·Node.js 우선순위를 존중하되 프레임워크·엔진·서버 구성을 확정하지 않는다.

## 책임 분리 후보

| 구성 | 책임 | 대응 화면 |
| --- | --- | --- |
| MainScreen | 게임 진입과 프로젝트 안내 | UX01 |
| HistoryMapScreen | 현재 시대의 지도와 선택 상태 | UX02 |
| EraPanel | 잠정 시대 목록과 진행 정보 | UX03 |
| RegionInfoPanel | 선택한 국가·지역의 자료 | UX04 |
| HistoryEventPanel | 사건과 관련 장소·시점 정보 | UX05 |
| MapViewport | 이동·확대·선택을 위한 지도 렌더링 경계 | UX02·UX04 |
| HistoricalContent | 시점·지역·세력·사건·출처 데이터 | 공통 |

React는 화면과 정보 패널을, TypeScript는 데이터와 상태의 구분을 담당하는 구성을 검토한다. 지도 렌더러는 SVG·Canvas·WebGL 등의 후보를 실제 요구와 성능에 따라 비교한다. Phaser 등 게임 엔진을 선결정하지 않는다.

## 데이터 모델의 후보

- Era: 시대 ID, 순서, 명칭, 검토 상태. 잠정 8개 구분을 고정 enum이나 장 수로 확정하지 않는다.
- TemporalExtent: 적용 시작·종료와 정밀도. 불확실한 연대를 단일 연도로 강제하지 않는다.
- Region / Place: 장소 식별자와 지리 자료 출처. 현대 행정구역과 역사 공간의 대응은 별도 검토한다.
- Polity: 국가·세력 식별자, 시점별 명칭. 한 국가에 하나의 고정 영토를 부여하지 않는다.
- SpatialEvidence: 도형, 적용 시점, 영역 종류, 불확실성, sourceIds, reviewStatus.
- HistoricalEvent: 관련 시점·장소·세력과 자료 상태. 설명 데이터와 게임 규칙을 분리한다.
- SourceRecord: 제목, 제공 기관, URL, 확인일과 해당 주장·자료와의 연결.
- PresentationClaim: 사실·해석·게임 창작 구분. 하나의 사건에도 여러 주장이 있을 수 있다.

검토 상태는 미검토·검토 중·검토 완료처럼 콘텐츠 검토를 표현하며 역사 자체의 확실성과 혼동하지 않는다. 게임적 가정은 별도 데이터로 연결한다.

## 화면 상태 후보

현재 화면, 시대, 지도 카메라, 선택 대상과 열린 패널을 구분한다. 지도 이동만으로 시대나 진행도를 변경하지 않는다. 시대 변경 시 해당 시점의 자료를 요청하고 선택 대상의 유효성을 다시 확인한다. 자료가 없거나 불확실하면 이를 표시하고 이전 시점의 영토로 대체하지 않는다.

## 구현 전에 필요한 결정

플레이어 역할과 반복 행동, 목표·보상·실패, 시대 진행 조건을 먼저 확정해야 한다. 이 결정 이후 저장 범위와 API·DB·서버 필요성을 판단한다. 인증·멀티플레이·결제·배포는 현재 요구사항으로 추가하지 않는다.

## 검증 방향

첫 구현에서는 시대와 공간 데이터가 올바르게 대응하는지, 빈·불확실 자료가 오인 없이 보이는지, 정보 패널에서 돌아와도 지도 맥락을 유지하는지를 검증한다. 게임 재미는 실제 반복 행동을 포함한 작은 프로토타입으로 별도 검증한다. 문서와 화면 목업만으로 재미나 학습 효과를 입증했다고 보고하지 않는다.
