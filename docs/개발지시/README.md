# 번호로 전달하는 개발 지시문

대표님이 검토한 지시문을 마이닷이 Git에 기록하고, 대표님이 개발 담당에게 번호를 전달하는 방식입니다. 기존 [역할 분담](../team-workflow.md)을 유지합니다.

**현재 발행된 개발 지시문은 없습니다.** 이 디렉토리는 사용법과 빈 템플릿만 제공합니다. 아래 `개발-00001`은 설명용 예시이며 승인·예약·개발 착수를 뜻하지 않습니다.

## 빠른 사용법

1. 마이닷이 대표님의 요청을 [템플릿](TEMPLATE.md)에 정리합니다. 대표님이 범위·완료 기준을 검토합니다.
2. 마이닷이 아래 번호 규칙에 따라 문서와 목록을 같은 PR에 기록합니다. 대표님이 승인한 **문서 버전·본문의 고정 커밋 링크·승인 근거**를 남깁니다.
3. 승인 기록까지 main에 반영된 뒤 대표님이 개발 담당에게 **“개발-00001 작업해줘”**처럼 번호를 전달합니다. 문서 정리 PR 병합과 개발 착수 승인은 별개입니다.
4. 개발 담당은 최신 main의 이 목록에서 해당 문서를 읽고 승인 버전과 범위를 확인한 다음 작업합니다. 번호를 확인한 최초 응답에 제목·버전·승인본 링크를 짧게 남깁니다.
5. 작업별 브랜치와 개발 PR에 번호를 넣고, 결과·검증·남은 사항을 지시문과 연결합니다. 마이닷이 목록을 갱신합니다.

개발 담당에게 처음 한 번 전달할 안내:

> RoxHistory에서 번호로 요청하는 작업은 최신 main의 `docs/개발지시/README.md`와 해당 번호 문서를 먼저 읽어 주세요. 대표님이 승인한 최종 버전과 착수 요청이 확인된 범위만 구현하고, 작업별 PR과 검증 결과를 같은 번호로 연결해 주세요.

번호만 조회하거나 문서가 존재하는 것은 착수 요청이 아닙니다. **대표님의 해당 번호에 대한 착수 요청과 확인 가능한 승인본**이 모두 있어야 합니다. 승인 대상이 모호하거나 문서에 접근할 수 없으면 필요한 내용을 확인하고 기다립니다. 문서 자체가 자동 실행 도구나 포괄적 권한은 아닙니다.

## 파일과 번호

- 형식: `개발-00001`, `개발-00002`처럼 5자리 숫자를 사용합니다. 파일명은 `개발-00001.md`처럼 번호와 일치시킵니다. 제목은 파일 안에 적습니다.
- `TEMPLATE.md`를 복사하되 빈 항목을 채우기 전에는 실행 가능한 지시문으로 취급하지 않습니다. 예시 파일에 실제 번호를 사용하지 않습니다.
- 번호 기록 담당은 마이닷으로 일원화합니다. 최신 main의 목록·파일과 진행 중인 번호 등록 PR을 함께 확인하고 사용·예약 이력의 최대 번호 다음을 선택합니다. 여러 등록 작업을 동시에 시작하지 않습니다.
- 문서와 목록을 같은 PR에 추가하고 PR 제목에도 번호를 표시합니다. 열린 등록 PR의 번호는 임시 예약입니다. 병합 직전 main과 다른 등록 PR을 다시 확인하고, 충돌하면 나중 등록 건의 번호와 링크를 함께 고칩니다. 이 절차는 수동 확인이며 자동 중복 검사가 설치된 것은 아닙니다.
- 발행한 번호는 바꾸거나 재사용하지 않습니다. 취소·대체된 문서와 목록 행도 보존합니다. 등록 PR을 취소할 때도 예약 번호와 PR을 취소 이력에 남겨 재사용하지 않습니다.
- 기존 `REQ-*`, `FOLLOW-*`, `IDEA-*`와 날짜별 지시문은 출처로 연결합니다. 자동으로 개발 번호를 붙이거나 미완료 항목 전체를 새 지시로 발행하지 않습니다.

## 승인과 버전

- 문서 상태: `초안 → 검토 중 → 승인`, 필요하면 `보류 / 취소 / 대체됨`으로 바꿉니다. 작업 상태는 별도로 `미착수 / 진행 중 / 검증 대기 / 완료`를 기록합니다.
- 문서 버전은 `v001`부터 올립니다. 승인 버전과 승인 대상 본문의 GitHub 고정 커밋 링크를 기록합니다. 승인 기록을 나중에 덧붙인 커밋은 승인 대상 본문 커밋과 달라도 되며, 본문이 같은지 확인할 수 있어야 합니다.
- 승인 뒤 범위·완료 기준·채택 에셋을 바꾸면 버전을 올리고 `검토 중`으로 되돌린 뒤 대표님의 재승인을 받습니다. 승인된 이전 본문은 Git 이력과 고정 링크로 보존합니다. 현재 문서가 다시 검토 중이면 예전 승인만으로 새로 착수하지 않습니다.
- 보류·취소·대체·승인 철회가 전달되면 이전 기록보다 우선합니다. 진행 중인 담당에게 알리고 영향 범위의 작업을 멈춘 뒤 재개 조건을 확인합니다. 다른 목적의 작업은 새 번호로 분리합니다.
- `main`에 반영된 목록은 찾기 위한 기준이고, 상세 범위는 해당 승인본이 기준입니다. 둘이 다르거나 여러 버전의 승인이 충돌하면 임의로 선택하지 않습니다.
- 문서 승인, 개발 착수, 구현 완료, 테스트 통과, 대표님의 체감 승인, main 병합, APK 공개 배포는 각각 구분합니다. 별도 승인 없이 병합·배포·권한 변경을 실행하지 않습니다.

### 취소된 번호 예약

현재 없음. 예약 후 취소된 번호가 생기면 번호·취소일·등록 PR·사유를 기록하고 재사용하지 않습니다.

## 개발 담당의 확인·보고

- 시작 전: 최신 main, [현재 개발 현황](../current-status.md), 승인본, 선행 작업, 이미 완료된 범위와 열린 PR을 확인합니다. [기존 개발 기준](../developer-instructions-current.md)은 참고 자료이며 미정 항목까지 이번 범위에 자동 포함하지 않습니다.
- 충돌 방지: 작업별 브랜치와 PR을 사용합니다. 예: `dev/00001-short-topic`, PR 제목 `[개발-00001] 작업 제목`. 등록 PR과 개발 PR을 구분하고, 변경 파일이 겹치면 먼저 조율합니다. 기존 작업을 덮어쓰거나 승인되지 않은 범위를 함께 넣지 않습니다.
- 완료 보고: 반영한 내용, 승인 기준별 결과, 실행한 검사와 실행하지 못한 검사, 남은 사항, 소스 커밋·개발 PR·화면/영상/보고서 링크를 남깁니다. 배포가 승인된 작업에만 APK·릴리스·해시를 추가합니다.
- `완료`는 합의한 완료 기준에 맞춰 기록합니다. 테스트 통과를 체감 승인으로, PR 제출을 main 반영으로 바꾸어 쓰지 않습니다.

## 공개 저장소 기록 원칙

이 저장소는 공개입니다. 지시문에는 공개 가능한 개발 요구사항과 근거만 적습니다. 비밀번호·API 키·토큰·서명 키·결제 정보·개인정보·비공개 대화 원문/스크린샷/내부 링크는 올리지 않습니다. 승인 근거는 공개 가능한 GitHub 댓글 링크 또는 승인자·일시·해당 버전·승인 범위를 최소한으로 요약한 기록으로 남깁니다. 비공개 승인의 진위를 확인할 수 없는 개발 담당은 대표님에게 확인합니다. 에셋은 출처·사용 권한·채택 버전을 적고 미승인 자료를 확정본으로 표시하지 않습니다.
